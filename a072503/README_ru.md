# OEIS A072503 — новые члены

**A072503**: number of ways to lace a shoe with n eyelet pairs such that there
is no direct "horizontal" connection between any adjacent eyelet pair.
В OEIS (снимок oeisdata от 20.10.2026) известны a(3..9). Здесь получены
**a(10) … a(400)**.

Английские версии основных документов: `README.md`, `explanation.md`,
`oeis_draft.txt`.

  не проверял, поэтому они **не** приняты.

## Определение (кратко)

Дырочки 1..n слева сверху вниз, n+1..2n справа снизу вверх; пары (k, 2n+1−k).
Шнуровка — порядок обхода всех 2n дырочек от 1 до 2n, в котором (а) нет
перехода внутри одной пары и (б) никакие три подряд идущие дырочки не лежат на
одной стороне. a(n) = (число таких порядков)/2: зеркальные пары, симметричных
нет. Точная формулировка — `DEFINITION.md`, а почему именно эта трактовка —
`DECISIONS.md` (D2). Только она даёт a(4) = 45 и a(5) = 1824, и она совпадает с
программой Irvine. Кроме того, те же правила без запрета горизонталей дают
ровно A078698 — родственную последовательность того же автора, Пфёртнера.

## Как воспроизвести каждое число

Всё запускается из папки `a072503/`. Нужны gcc с OpenMP и Python 3.8+ с numpy
(нужен методу 1, `method_dp/dp_main.py`, и скриптам в `recurrence/`).

| что | команда | время (4 ядра, 16 ГБ) |
|---|---|---|
| выбор трактовки, n = 3..5 | `python3 brute/interpretations.py 5` | 0,5 с |
| полный перебор, a(3..8) | `gcc -O3 -march=native -fopenmp -o brute/brute_dfs brute/brute_dfs.c && for n in 3 4 5 6 7 8; do brute/brute_dfs $n; done` | n = 8: около 59 с |
| прямая DP по подмножествам, a(3..12) точно | `gcc -O3 -march=native -fopenmp -DMODE=0 -o brute/subset_dp_m0 brute/subset_dp.c && for n in $(seq 3 12); do brute/subset_dp_m0 $n; done` | n = 12: 13 с, 3 ГБ |
| прямая DP, a(13) (по модулю 2^64 и по модулю 2^61−1, затем КТО) | см. команды под таблицей | около 24 с + 15 с, 6,4 ГБ |
| **метод 1**, a(3..400) | `python3 method_dp/dp_main.py 400` | 253 с, 1,3 ГБ (n ≤ 100: 1,6 с) |
| **метод 2**, a(3..500) | `python3 method_ie/ie_dp.py 500` | 58 с, 0,3 ГБ (n ≤ 200: 1,3 с) |
| сверка сохранённых результатов, `accepted_terms.txt` | `python3 compare.py` | < 1 с |
| короткие программы, a(3..15) / a(3..17) | `python3 method_dp/short.py`, `python3 method_ie/short.py`, `python3 oeis/a072503_oeis.py` | < 0,1 с |
| D(n)/(n−1)! = «канонические» шнуровки | `python3 brute/canonical_check.py 6` | 8 с |
| поиск рекуррентности | `(cd recurrence && python3 guess_np.py T 40 ../method_ie/results.txt && python3 holdout.py 18 18 420 2147483629)` | 2 мин + 12 с |

**a(13) прямой DP.** Программа запускается дважды, по модулю 2^64 и по модулю
2^61−1, и `brute/crt.py` объединяет два остатка (каждый запуск печатает в
stdout `D=` и остаток; ход работы идёт в stderr):

```
gcc -O3 -march=native -fopenmp -DMODE=1 -o brute/subset_dp_m1 brute/subset_dp.c
gcc -O3 -march=native -fopenmp -DMODE=2 -o brute/subset_dp_m2 brute/subset_dp.c
D1=$(brute/subset_dp_m1 13 | sed 's/.*D=\([0-9]*\).*/\1/')
D2=$(brute/subset_dp_m2 13 | sed 's/.*D=\([0-9]*\).*/\1/')
python3 brute/crt.py 13 $D1 $D2    # n=13 CRT: D=... a=1000447433001080064000
```

`python3 compare.py` ничего не пересчитывает. Он сверяет сохранённые
результаты двух методов (`method_dp/results.txt`, `method_ie/results.txt`)
между собой, со значениями прямой DP из `logs/subset_dp_exact_n3-12.log` и
`logs/subset_dp_crt_n12-13.log` и с `oeis/b072503.txt`; если все проверки
прошли, он перезаписывает `accepted_terms.txt` тем же содержимым.

Программы `dp_main.py` и `ie_dp.py` возобновляемые. Они дописывают по строке
на каждое n, пишут лог (`progress.log`), сохраняют контрольные точки в `tmp/`
(в git не попадают) и останавливаются по лимиту времени (по умолчанию 20 и
23 минуты). Если `results.txt` уже есть, повторный запуск пересчитывает и
**сверяет** каждую строку, а не перезаписывает её. Но это верно только при
запуске **без контрольной точки**: в конце каждого запуска она сохраняется, и
следующий запуск продолжит с неё, ничего не сверяя. Поэтому для повторной
проверки сначала удалите `method_dp/tmp/checkpoint.pkl` и
`method_ie/tmp/ie_dp.ckpt` (или запускайте
`python3 method_ie/ie_dp.py 500 --no-ckpt`).

Повторный запуск дописывает строки в `method_dp/progress.log` и
`method_ie/progress.log`, которые отслеживаются git: в репозитории лежат логи
исходных запусков 20.10.2026. После повторного запуска верните их командой
`git checkout -- method_dp/progress.log method_ie/progress.log`.

## Как установлены числа

1. **Проверка приоритета**: `seq/A072/A072503.seq` из github.com/oeis/oeisdata
   (sparse checkout, коммит f72d165 от 20.10.2026, копия
   `A072503_oeisdata_snapshot.seq`). a(10) там нет, keyword `more`.
2. **Определение** восстановлено перебором и совпало с известными a(3..8)
   (`brute/`, `logs/`).
3. **Два независимых быстрых метода** написали два разных агента. Каждому
   было предписано читать только `DEFINITION.md` (там есть известные члены) и
   свою папку, наших промежуточных чисел им не давали. По файлам это
   проверить нельзя; проверяющий не нашёл признаков заимствования.
   * `method_dp/` — динамика по состояниям: сколько рядов не тронуто, с
     занятой только левой и с занятой только правой дырочкой, плюс несколько
     битов локальной информации. Около n³ состояний.
   * `method_ie/` — сумма по шаблонам сторон (слова из L/R без LLL и RRR),
     горизонтали учтены включениями-исключениями. Формула:
     `2a(n) = (n−1)! Σ_k (−1)^k (n−1−k)! N(n,k)`.
   Оба воспроизводят a(3..9) и сверены с собственными переборами.
4. **Третья проверка**, без всякой симметрии — прямая DP по подмножествам
   (`brute/subset_dp.c`), n = 3..13.
5. **Сверка** (`compare.py`, `logs/compare.log`): методы 1 и 2 совпадают для
   n = 3..400, прямая DP совпадает с ними для n = 3..13. b-файл
   `oeis/b072503.txt` совпадает с принятыми членами n = 3..233.
6. **Проверяющий агент** (`review/REVIEW.md`) искал ошибку и **не нашёл её** ни
   в трактовке, ни в коде, ни в числах. Он сделал следующее:
   * заново собрал оба `results.txt` с нуля, побайтно совпало;
   * написал собственный перебор «канонических» шнуровок, который даёт a(3..11)
     напрямую, включая a(10) (`review/canon_enum.c`);
   * написал третий быстрый метод (`review/glue_ie.py`), он совпал для n = 3..500;
   * проверил ключевую лемму метода 1 на 882 тыс. реальных начал шнуровок;
   * проверил формулу метода 2 по каждому слову сторон для n = 3..9;
   * нашёл ещё одно подтверждение трактовки: те же правила без запрета
     горизонталей дают соседнюю A078698 Пфёртнера.

   Вердикт: a(10) и все a(3..400) установлены. Его замечания касались только
   документации; что с ними сделано — `DECISIONS.md`, D5.

## Формулы: что доказано, что нет

* **Доказано** (доказательства написаны ИИ-агентами и проверены
  агентом-проверяющим, но ещё не независимым специалистом-человеком): формула
  включений-исключений (`method_ie/METHOD.md`; там же явная 6-кратная
  биномиальная сумма) и точность метода 1 (`method_dp/METHOD.md`).
  Также доказано, что 2a(n) делится на (n−1)!: частное — число шнуровок, в
  которых внутренние пары впервые встречаются по порядку 2..n
  (`explanation_ru.md`, раздел 4). Перебором проверено до n = 6, а
  проверяющий — до n = 11.
* **Только гипотеза:** 2a(n)/(n−1)! удовлетворяет линейной рекуррентности
  порядка 18 с многочленными коэффициентами степени 18. Она найдена по модулю
  простых чисел, подогнана по n ≤ 420 и выполняется для всех следующих членов
  до n = 500. Коэффициенты не выписаны (`recurrence/README.md`).

## Затраченное время

* Вся работа — около 1 ч 20 мин (18:56–20:15 UTC, 20.10.2026). Агенты методов 1
  и 2 работали параллельно ~18 и ~28 минут, проверяющий — ~37 минут
  (19:33–20:10).
* Чистое машинное время на новые числа — несколько минут (таблица выше).
  Самое долгое — полный перебор n = 8 (около 59 с) и метод 1 до n = 400 (4 мин).
  Ни один запуск не подходил к лимиту в 25 минут.
